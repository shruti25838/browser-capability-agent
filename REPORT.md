# Design Report - Computer-Use Automation System

## 1. Architecture

The system has two phases that barely share any code path on purpose. Discovery is where an LLM is in the loop, and it only runs once per capability. Replay has no LLM at all, and it's what actually gets invoked every time the capability is used in production.

Modules:

- **Perceiver** reads the current page state through Playwright's accessibility tree (role and accessible name). For tables it has two helpers: `find_row`, which locates a row by matching text it contains rather than its index, and `resolve_column_index`, which matches a column by its header text instead of its position. Both discovery and replay use the same Perceiver, so they "see" the page the same way.
- **DiscoveryAgent** runs the observe, decide, act loop. It hands the LLM (Gemini) a fixed set of tools (`find_row`, `click`, `type`, `extract`, `finish`), runs whatever tool it picks through the Perceiver, and keeps going until the model calls `finish`. All it produces is a `DiscoveryRun`, a full trace of what happened. It never touches the replay path.
- **ArtifactWriter** takes a successful `DiscoveryRun` and turns it into a versioned `Artifact`. This is where generalization happens. Literal values used during discovery, like a name typed into a search box, become named typed parameters. Literal values read out during discovery, like an extracted balance, become typed outputs instead of getting baked into a success check.
- **ReplayEngine** takes a saved `Artifact` plus a dict of input parameters, resolves the placeholders, and walks through the steps using the same Perceiver, checking each pre/postcondition with a bounded retry. It returns a structured result. There's no LLM call anywhere in this module.
- **GuardrailChecker** does one job: an allowlist check on domain and action type, run before every action in both phases. Discovery can't wander outside scope just because it's "still exploring."
- **EscalationHandler** kicks in only on a `hard_failure` during replay. It keeps the live browser session open, logs what happened, and waits for a human to either fix the live page and resume, or abort.

One trade-off worth calling out: I kept this as a single Python process instead of splitting it into services. The brief specifically says not to build scaling infrastructure prematurely, and a single process is enough to prove out the contracts that actually matter (the artifact schema, the result contract) and those are what would need to survive a move to multiple services later anyway. I drew the module boundaries with that in mind, so splitting into services down the line would mean moving files around, not redesigning interfaces.

## 2. Artifact schema

The artifact isn't just a list of steps, it's meant to work as a callable contract. Each step has:

- a **precondition**: what has to be observably true before the step acts, so it doesn't fire on the wrong screen
- the **action** itself (`click`, `type`, `find_row`, `extract`), with a locator that's either role/name based (accessibility tree) or content based for tables, never based on position
- a **postcondition**: what has to be true after the step acts, which doubles as the replay checkpoint
- an **outcome_mapping**: an optional list of named business outcomes tied to specific conditions, so a step can report something specific ("no such member," a validation error) instead of a generic pass/fail when its own condition comes back cleanly false

At the artifact level there's typed input parameters (generalized from literals used during discovery), typed outputs (generalized from literals extracted during discovery), an overall success condition, a version number, and some metadata like the goal text, target URL, and creation time.

I shaped it this way because the brief's own glossary flags "business outcome vs. failure" as the most common mistake people make here, and postconditions are what actually make that distinction possible. Without an expected post-state to check against, replay can only tell you the click didn't throw an error, not whether it actually landed where it was supposed to.

There's a real bug I ran into here that's worth walking through. The first working artifact I generated hardcoded the actual result of that one discovery run (`expected_value: "$100.00"`) into both the extract step's postcondition and the overall success condition. That meant replaying the same artifact with a different input would extract the right new value, but then fail its own success check because it was still comparing against the first run's answer. The root cause was that the generalization logic only substituted literals that matched a declared input parameter, it had no concept that a literal could also be an output that legitimately changes from run to run. The fix was to have `ArtifactWriter` cross-reference extracted values against the run's own outputs, and if a condition's literal matches one of those, rewrite it to a new `VALUE_EXTRACTED` kind that just asserts something non-empty of the right type was produced, instead of pinning it to a specific value. Genuine fixed constants, like a literal confirmation message unrelated to any extraction, still pass through untouched. I kept both the buggy and the fixed artifact in `/evidence/` so it's easy to compare.

## 3. Determinism and error handling

Replay never calls an LLM. Every locator resolves the same way discovery resolved it, role and name through the accessibility tree, or content match for tables, so the "how do I find this thing" logic is identical between the two phases. The only thing that differs is the "what to do next" decision, which is an LLM during discovery and a fixed script during replay.

Each precondition or postcondition check gets retried up to 2 times, about a second apart, before it's treated as failed. This is a retry on the check, not on the action, it re-observes the same condition on the assumption that some failures are just the page catching up (a table still rendering, something loading asynchronously) rather than a real problem. Retrying the action itself is deliberately out of scope for the core replay loop, mostly to avoid something like double-submitting a form.

Once retries are exhausted, the result falls into one of three buckets, returned as a structured result rather than a plain true/false:

- **success**, outputs come back as declared
- **business_outcome**, a condition is legitimately false, not broken. Any step can declare an `outcome_mapping`, a list of named business outcomes tied to specific conditions, so a step isn't limited to a generic pass/fail, it can report something like `outcome_name: "not_found"` or a validation-style outcome a discovery run identified. `find_row` still has a built-in fallback for this (row-visible/row-absent) so existing artifacts without an explicit mapping keep working the same way they always did
- **hard_failure**, everything else. A condition still false after retries with no matching outcome rule, a guardrail block, or any exception raised while checking. An exception always counts as a hard failure regardless of any declared outcome mapping, because an error means something is actually broken, not that the answer happens to be a known outcome

That exact rule is pinned down as a parametrized test in `test_replay_classification.py`, not just written down in prose somewhere it could quietly drift out of sync with the code.

Worth being direct about where an `outcome_mapping` rule actually comes from: discovery only ever sees the happy path it walked, so if a rule names something like a permission denial or a validation error, that's the model guessing at a state it never directly observed during that run. I think that's fine, but only because of what the artifact is for. Discovery proposes the outcome rules, they don't take effect until a human reviews and approves the artifact before it goes to production, and the artifact itself is the review surface, someone reading the JSON can see exactly which conditions the system will treat as business outcomes versus failures, and correct it before it's ever replayed against a live account. The schema is what makes that review possible in the first place.

The brief also draws a three-way distinction I've partly collapsed: business outcome, recoverable condition, and hard failure. My three result buckets are success, business_outcome, and hard_failure, which isn't quite the same axis. Recoverable conditions are handled inside the check loop rather than surfaced as their own result bucket, retry is the only recoverable class actually implemented, there's no dismiss-a-known-interstitial handling yet. A `recovery` field on `Step`, sitting alongside `outcome_mapping`, would be the natural way to add that as a first-class thing rather than an invisible retry, and it's listed in Cuts.

The result also now says whether anything needed a retry to pass. Each check records whether it recovered on a retry rather than passing clean the first time, rolled up into a top-level `recovered_via_retry` flag, so it's visible whether a run went smoothly or only succeeded because a recoverable condition (a slow load, a transient state) resolved itself partway through.

## 4. Heterogeneity and multi-tenant

**Surface abstraction.** The seam here is the Perceiver. It's the only module that knows how to read a live page; everything downstream of it, the artifact schema, the locator types, the replay engine, only knows what it read: a role, a name, a scoped row. I think about this as a degradation ladder, and it's worth being precise about which rungs actually exist versus which ones are just designed for:

1. Accessibility tree, role plus name. Built, this is the primary signal everywhere today.
2. Content-based scoping within a region when names are duplicated or too generic to disambiguate on their own, using something like `scope_selector` to narrow the search to a specific subtree first. Built, this is exactly the problem `scope_selector` solves on a page with two identical tables.
3. Screenshot plus coordinates as a second Perceiver implementation behind the same interface, for a surface where the accessibility tree comes back mostly unlabeled generic nodes, a genuine legacy frameset with table-based layout and no ARIA. Not built. This is deliberately not a DOM-selector fallback, since a page that fails this badly typically has no stable selectors either, that's the same underlying problem that ruled out DOM selectors as the primary strategy in the first place. Screenshot plus coordinates is the honest fallback of last resort, and because it sits behind the same Perceiver interface, nothing above it, the artifact schema, the replay engine, would need to change to support it.

To extend to a desktop app, rung 1 would mean swapping the Perceiver's backend from Playwright's accessibility snapshot to the OS-level accessibility API (Windows UIA or macOS AX), and the locator types in the artifact schema wouldn't need to change at all, since "role plus name" and "value in a cell relative to a labeled row" exist in both browser and desktop accessibility trees. The artifact format is meant to be surface-agnostic on purpose, only the Perceiver's implementation is tied to a specific surface.

**Multi-tenant reuse.** Since a lot of tenants run the same underlying vendor product just configured or branded differently, an artifact recorded against one tenant's instance should be reusable across the others, as long as its locators are stable identifiers (role, name, content) rather than tenant-specific literals like a bank's logo text or a specific URL. I'd extend the schema with:

- a `product_id` and `product_version` field on the artifact, separate from any single tenant's URL, so an artifact reads as "a capability for this vendor product," and a tenant just supplies its own base URL and parameters at replay time
- a per-tenant override layer, a small optional patch keyed by tenant, resolved against the base artifact for the tenant's `product_id`, that can swap out a step's locator or add an extra step for that specific tenant's configuration divergence (an extra confirmation dialog one tenant turned on, a renamed field). Keying by tenant rather than by `product_id` matters here: every tenant on a given product shares the same base artifact, but the override itself has to be tenant-specific, or every tenant on that product would get the same patch, which defeats the point of having overrides at all. The base artifact stays canonical and overrides are additive, so they can be reviewed independently
- drift detection across tenants, which I didn't build but did design for. Replay already fails loudly and specifically (a precondition/postcondition mismatch with the expected vs. observed detail), which covers most of what you'd need to notice drift in the first place. Turning that into something proactive would mean periodically replaying a canary run per tenant and tracking the failure rate over time, a monitoring layer on top of the same result contract rather than a redesign of it

## 5. Escalation and handoff

Escalation only triggers on `hard_failure`, not on `business_outcome`, since a legitimate "not found" answer doesn't need a person. When it does trigger, `EscalationHandler`:

1. leaves the live Playwright page open instead of closing or replacing it
2. takes a screenshot and logs an intervention request (goal, step, expected vs. observed, reason) to an append-only log
3. waits for a human signal, standing in for a real operator console per the brief's scope note. The person can actually click around in the same open browser window by hand
4. on resume, re-checks the specific condition that originally failed, on the same page object. If it now holds, the replay loop picks up where it left off. If not, or if the human aborts, it returns a hard failure noting that intervention was attempted

The control-transfer model behind this is simple: there's exactly one live session per run, and it's never ambiguous who's driving, either the replay loop or a human, never both at once, and the handoff is a blocking wait rather than a race. That's not just implied by log ordering, there's an explicit owner field (`automation` or `human`) on the run itself, flipped to `human` the instant escalation takes over and back the moment control returns, and it shows up both in the final result and in the intervention log entries. I didn't just design this, I checked it works: a test in the suite injects the missing element mid-escalation (standing in for a human fixing the page) and confirms the same run picks back up and finishes successfully on the same session, with the owner field flipping back correctly. This is one of the 116 automated tests, not a one-off manual check, so it keeps running every time the suite does.

## 6. Safety

- **Allowlist**: `GuardrailChecker` enforces a domain allowlist and an action-type allowlist, checked before every action in both discovery and replay. An LLM exploring during discovery is bound by the exact same rules as deterministic replay, it doesn't get a looser leash just because it's "still figuring things out."
- **Risky vs. reversible actions**: every action type in the allowlist carries a reversibility tag, `safe`, `requires_confirmation`, or `blocked`, checked at the same guardrail call site as the domain/action check rather than as a separate system. `requires_confirmation` actions won't run at all unless the caller explicitly passes `--allow-confirmed-actions`, and `blocked` actions never run no matter what flag is set. I didn't just leave this as a design idea, I built it against something real: the target page's delete link is tagged `blocked`, and there's a test confirming an attempt to click it gets refused by `GuardrailChecker` before the click ever reaches Playwright.
- **Prompt injection**: the accessibility-tree snapshot handed to the LLM during discovery is wrapped and labeled as untrusted observed data (a `<page_state>` block, with a system prompt warning that content inside it is data, not instructions), since a legacy page could contain text crafted to look like a command. The actual line of defense, though, isn't the prompt wording, it's the guardrail allowlist, and there's a test proving that directly: a tool call shaped like what a successfully manipulated LLM might emit (a `delete` click) still gets refused by `GuardrailChecker.check_action`, regardless of why the model proposed it. It's the same risk-tiering mechanism from above, reused here, since the LLM's own behavior is never treated as the last line of defense.
- **Step and time budgets**: discovery is bounded by both a max step count and a wall-clock timeout, both configurable through CLI flags, and returns a distinct "budget exceeded" result instead of looping forever or crashing. Replay's retry logic was already bounded (2 retries per condition, no unbounded loop), I confirmed that rather than added anything new there.
- **Sensitive data**: no credentials or secrets get stored in artifacts, only role/name/content-based locators and typed parameter names. API keys come from environment variables and never get logged. There's a regex-based redaction pass on everything else written to disk, evidence logs, the intervention log, console output, that scrubs SSN-shaped, credit-card-shaped, and long-digit-sequence patterns before they're written. An artifact's own declared output values (say, an extracted due amount) are deliberately exempt from redaction, since that's the actual output the capability is supposed to return, not incidental data it happened to see along the way.
- **Audit log integrity**: entries in `intervention_log.jsonl` are hash-chained, each one stores a SHA-256 of the previous entry, and there's a verification function that walks the log and reports exactly where the chain breaks if a line's been altered or removed after the fact. That catches tampering, it doesn't prevent someone with disk access from rewriting the whole file and chain from scratch, so it's tamper-evident rather than tamper-proof. A real deployment would want this log shipped somewhere append-only instead of sitting on local disk.
- **Blocked vs. escalated, and a gap I'll own here**: section 3.6 lists a risky step needing a person to decide as a reason to escalate, but `blocked` actions in this system are refused outright rather than routed to a human. That's a deliberate choice, not an oversight: in a regulated environment I don't think an action tagged destructive should ever run automatically, even with a human's sign-off through this particular channel, since a live escalation prompt is a thin thing to hang an irreversible action on. Where I do think this needs more work is `requires_confirmation`, which right now is authorized ahead of time through a CLI flag (`--allow-confirmed-actions`) set before the run starts, not a live decision made by a person at the moment the action is about to happen. That's closer to a pre-approval than a real escalation. With more time I'd route `requires_confirmation` actions through the same `EscalationHandler` used for `hard_failure`, so a person makes the call live, on the actual session, instead of a flag someone set an hour earlier covering every confirmation the whole run might hit.

## 7. Cuts

What I left minimal or skipped entirely, and why:

- **Operator console**: a mocked, blocking-prompt handoff instead of a real co-browsing UI, which the brief's scope note explicitly allows. The handoff mechanism and control-transfer model are real, the UI around it isn't.
- **Multi-tenant and desktop support**: designed for in section 4 but not built, since the brief says not to implement this.
- **Automated browser-driven end-to-end tests**: the unit suite (116 tests) covers schema round-tripping, guardrails, parameter resolution, replay classification, artifact generalization, escalation edge cases, and the prompt-injection/risk-tiering defense, all without touching a live browser or LLM. The actual end-to-end paths, a successful discovery run, a successful replay, cross-person generalization, a business_outcome demo, and a hard_failure demo with escalation (including a real crash I found and fixed while testing), are verified through real saved runs in `/evidence/` instead of an automated harness, mostly because running a live browser plus an LLM in CI is slow and flaky for what it'd actually buy.
- **Tamper-proof audit logging**: the hash-chained log is tamper-evident, not tamper-proof, it can't stop someone with local disk access from rewriting the file and chain together. A real deployment would ship this log to append-only storage instead of trusting the local filesystem.
- **Proactive drift detection**: replay catches drift reactively, as a clear failure when it happens, but nothing monitors for it across runs ahead of time.
- **A live discovery example of a non-find_row business outcome**: the outcome mapping mechanism (any step can declare a named business outcome, not just find_row) is proven by a unit test, not by a real discovery run, since the target flows I built against didn't naturally produce a validation error, permission denial, or similar outcome outside of find_row's "not found" case. The mechanism is real and tested, but I'd want one more live discovered example before calling this fully proven end to end.
- **Rung 3 of the surface degradation ladder**: screenshot plus coordinates, described in section 4, isn't built. Everything today runs on rungs 1 and 2 (accessibility tree, plus content-based scoping), which is enough for this target but wouldn't be enough for a genuinely unlabeled legacy frameset.
- **A first-class recoverable tier**: right now the only recoverable behavior is the retry inside the check loop. Something like dismissing a known interstitial isn't handled, and there's no way for a step to declare "if you see this, do this one specific recovery action and continue" the way `outcome_mapping` lets it declare named outcomes. A `recovery` field on `Step`, checked before falling through to a retry or a hard failure, is the natural next piece here.

With more time, next up would be the per-tenant override layer, a canary-based drift detector, and shipping the audit log to append-only external storage instead of local disk.
